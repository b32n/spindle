# Import loss report

Spindle models a subset of Excel, Word and PowerPoint. Instead of dropping the rest silently, every importer can tell you **what it cannot preserve**
before the open document is replaced.

```ts
import { inspectWorkbookFile, importWorkbookFile, hasImportLoss, describeImportLoss } from '@b32nio/spindle-sheets-react';

const report = await inspectWorkbookFile(file);   // read-only: nothing is imported
if (hasImportLoss(report)) {
  console.log(describeImportLoss(report));
  // ['2 × conditional formatting rule(s) (Sales) — not imported', '1 × chart(s) — not imported']
}
const { warnings, loss } = await importWorkbookFile(workbook, file); // `loss` is the same report
```

Docs: `inspectDocumentFile(file)` / `importDocumentFile(doc, file)` from `@b32nio/spindle-docs-react`. Core (no React):
`inspectXlsx(bytes)`, `inspectCsv(text)` in sheets-core, `inspectDocx(bytes)` in docs-core, or `detectXlsxLoss` / `detectDocxLoss` / `detectCsvLoss`
from `@b32nio/spindle-io/{xlsx,docx}` (XLSX/DOCX) and `@b32nio/spindle-shared/export/csv`. PPTX: `detectPptxLoss(bytes, { detail })` from
`@b32nio/spindle-io/pptx` and `inspectDeckFile(file)` / `importDeckFile(deck, file)` from `@b32nio/spindle-slides-react` (the toolbar's Open uses them and shows the import dialog; `inspectPptx` is in slides-core, and the io reader `importPptx` from the same subpath is being completed in stages, see the PPTX table below).

`ImportLossReport` is `{ format, items: ImportLossItem[] }`; an item is `{ id, label, count, where?, effect, state? }` with a stable `id` such as
`xlsx.conditionalFormatting`. `state` (`'lost'` when absent, `'approximated'`, or `'kept'`: stored unchanged for saving back, but not editable) lets the dialog list
"Kept, not editable" apart from "Will be lost"; ids stay stable and only counts, effect text and state change as constructs become preserved.
Parts an importer keeps opaquely live in the `@b32nio/spindle-shared/opaque` store (content-addressed, size-capped; a part over the cap is reported as `lost: too large`). The store returns copies from `get`/`list`, and `put` reports `contentTypeConflict` when equal bytes arrive under a different content type (the first type is kept; importers should surface it). Parts are hashed with SubtleCrypto (SHA-256), which browsers expose only in secure contexts (https or localhost): on a plain-http page `put`/`hashBytes` reject with `SubtleCrypto unavailable`, so hosts must serve over https. An empty `items` list means nothing detectable is lost. The scan is a cheap pre-pass over the zip (no workbook
model is built) and never throws on a malformed file; the import itself reports that error. The XLSX fidelity harness (`fixtures/xlsx/`,
`npm run sheets:xlsx-fidelity`) records this report for every corpus file next to a package ledger that accounts for each part of the file.

## What is reported

| Format | Reported |
|---|---|
| XLSX | conditional formatting, data validation, filters, protected sheets / workbook protection, grouped rows/columns, sparklines, hidden sheets (become visible), named ranges, charts, images, comments/notes, tables, pivot tables, macros, external links, slicers, rich text inside cells, formulas that use functions the editor does not have (`xlsx.formulas.unsupported`), formulas with table (structured) references (`xlsx.formulas.structuredRefs`), number formats the editor cannot show like Excel: kept as written and saved unchanged, but shown in General or with English month and day names (`xlsx.numberFormats.approximated`) |
| DOCX | tracked changes that cannot be kept (formatting changes of a paragraph mark's own formatting or of a table or section, a change inside a field result, around an image or a note reference; insertions, deletions, moves and formatting changes of text, paragraph marks and table rows are kept), content controls that cannot be kept (repeating sections, data-bound, group, row- or cell-level controls: their content is kept, the control lost), footnotes and endnotes that nothing in the body refers to, floating images, text boxes/shapes, equations, embedded objects, charts/diagrams, multi-column sections (kept for export, laid out as one column), tables of contents that cannot be read as a block and indexes (text kept, field lost), legacy form fields (text kept as plain text) |
| PPTX | **`importFromPptx` in `slides-core` imports decks (the toolbar's Open and Download buttons, behind `fileActions`, use it)**; the io reader reads text and shapes (see the PPTX loss ids), so ids it reads say `kept`/`approximated` and the rest are `lost: not imported`. Detected: charts, SmartArt, audio and video, embedded objects, transitions, animations, comments, macros, hidden slides, speaker notes, fonts the editor may not have, shapes with a geometry outside its library of 76 presets or custom geometry, EMF/WMF pictures, encrypted and legacy `.ppt` files, size limits (detector only; the full level adds 43 finer ids) |
| CSV | semicolon- or tab-separated files (they import into one column) |

### XLSX loss ids

`inspectXlsx(bytes, { detail })` (sheets-core) and `detectXlsxLoss(bytes, { detail, knownFunctions, isNumberFormatExact })` (`@b32nio/spindle-io/xlsx`)
parse the package XML (entities are never expanded, oversized parts are skipped and named, nothing throws). The default `detail: 'summary'` is what the
confirmation dialog shows; `'full'` adds the finer ids below and is what the XLSX fidelity harness records. Every `effect` starts with a state word:
`lost:` (not kept at all), `approximated:` (kept in a weaker form) or `kept:` (kept, listed for information). Formula counts are per formula cell (every cell of a shared formula counts with its master's functions and references). Counts are of objects, not of package
parts: a chart is one chart however many parts it has, a picture is one picture however many times its image file is used.

Summary ids (dialog): `xlsx.conditionalFormatting`, `.dataValidation`, `.autoFilter`, `.sheetProtection`, `.workbookProtection`, `.outline`, `.sparklines`,
`.hiddenSheets`, `.definedNames`, `.charts`, `.images` (pictures, sheet backgrounds and pictures in cells), `.comments` (sheets with notes or threads),
`.tables`, `.pivotTables`, `.macros`, `.externalLinks`, `.slicers`, `.richText`, and three new ones: `xlsx.formulas.unsupported` (`where` = function names;
a function counts as supported when the editor's formula catalog has it after the `_xlfn.`/`_xlws.` prefix is removed; only reported when the caller passes
`knownFunctions`, as `inspectXlsx` does), `xlsx.formulas.structuredRefs` and `xlsx.numberFormats.approximated` (`where` = the codes; only reported when the caller passes `isNumberFormatExact`, as
`inspectXlsx` does, which since plan S3 means: the number-format engine reads the code and shows it as Excel does. Every code is kept verbatim, as a structured
format when that writes the very same code back and as `custom` otherwise, so a save never changes it; what is still reported is a code the engine cannot read
(not valid in Excel, a non-Gregorian calendar, `[DBNum1]`), a date or time tagged with another language (`[$-407]dddd`: month and day names would be English),
and a built-in id with no code, such as the era dates 27 to 36 of the Asian locales. Before S3 the check was "maps to a structured format", which flagged
every date, time, fraction, elapsed, scaling and literal code: 66 occurrences in 3 of the 43 corpus files, now 0). The effect text says so: the code is kept as written and saved unchanged, but shown in General or with English month and day names.
`xlsx.formulas.cachedOnly` (state `kept`) counts the formulas the editor cannot evaluate: a function it lacks (what `xlsx.formulas.unsupported` lists by name), text its
engine cannot parse, a table (structured) or defined-name reference, an external workbook reference. Only reported when the caller passes `knownFunctions` or
`isFormulaEvaluable`, as `inspectXlsx` does; the importer decides by the same test, so the report and the import agree. See "Formula interchange and cached values" below.
`xlsx.formulas.wholeColumn` (whole-column and whole-row references, `A:A`, `1:1`) is no longer reported: the engine evaluates them (plan S5), so they are not a
loss. A formula using one still appears under `xlsx.formulas.unsupported` if it calls a function the engine lacks.

### Formula interchange and cached values (S4)

**Prefixes.** Excel writes functions newer than the 2007 file format with `_xlfn.` (`_xlfn.IFS`, `_xlfn.XLOOKUP`, `_xlfn.STDEV.S`), the
dynamic-array ones with `_xlfn._xlws.` (`FILTER`, `SORT`), the parameters of `LET` and `LAMBDA` with `_xlpm.`, and writes `@x` as
`_xlfn.SINGLE(x)` and `A1#` as `_xlfn.ANCHORARRAY(A1)`. The importer reads these as the plain spellings the editor shows and evaluates, and the
exporter writes the prefixes back (`FUTURE_FUNCTIONS` in `packages/io/src/xlsx/future-functions.ts` is the table; `fromFileFormula` and
`toFileFormula` are exported from `@b32nio/spindle-io/xlsx`). String literals, quoted sheet names and bracket groups are never rewritten.

**Saved results are the values.** An imported workbook shows the results the file saved. The editor recalculates a formula when a cell it
refers to changes or when the user edits it, not wholesale on load; a formula with no saved result, a volatile one (`NOW`, `RAND`, `OFFSET`,
`INDIRECT`...) and an array formula that spills are evaluated on load. The host option `recalculateOnLoad` (`importFromXlsx` option,
`importWorkbookFile` option, `recalculateOnLoad` prop of `WorkbookCanvas`; default off) evaluates every formula the engine can evaluate on load
instead. Two limits: undo and redo, and a collaborator who joins a room, recalculate the formulas the engine can evaluate (the saved result
is kept by the client that imported the file; the cached-only cells below are the same everywhere).

**Cached-only formulas.** A formula the engine cannot evaluate is never shown as `#NAME?`: the cell is marked `cachedOnly`, shows the result the
file saved, keeps the file's formula text exactly (prefixes included, so the formula bar shows what Excel wrote) and is written back with both:
the saved value and the formula are kept; the formula's cell references follow row and column insert and delete (they do not follow anything else, see below). It is reported as `xlsx.formulas.cachedOnly`. **The value can be out of date**: a cached-only cell does not follow the cells it
refers to, and a cell that depends on it reads its saved value. **Its references do follow structural edits**: inserting or deleting rows or columns rewrites the cell
references in its text (`A1`, `$A$1`, `A1:B2`, `A:A`, `1:1`, `Sheet2!A1`, `'My Sheet'!A1:B2`) with the outcome of a normal formula's, and only those
bytes change (whitespace, case, string literals, function names, structured references and text the grammar rejects are copied as written). A
reference into deleted rows or columns becomes `#REF!`, a range keeps the rows or columns of it that survive and is `#REF!` only when all of them are deleted (as in Excel and for a normal formula), a
reference to another sheet only moves when that sheet is edited, and 3D references, references to sheets that do not exist and external workbook
references stay as they are (as for a normal formula). Sorting leaves the text as it is, and the engine has no move operation: copying or filling
a cell rebases a formula it can parse and drops the cached-only mark (below). Undo restores the original text. The saved value stays, so Excel
recalculates the formula when the file is reopened, possibly to a different result. The formula bar says that the value is a saved one ("Saved
value", with the caveat as tooltip and accessible name). Editing the cell (a value or a formula) removes the mark. Copying such a cell to another place copies its text, which the
engine cannot evaluate: the copy shows `#NAME?` until the formula is changed. Defined names are not imported yet, so a formula that uses one is
cached-only too.

**Array and dynamic-array formulas.** `t="array"` formulas keep their range. One the engine can evaluate is evaluated on load: a legacy
(CSE) array formula keeps the extent the file gave it (its result is cut to it, or padded with `#N/A`, as Excel shows it), a dynamic-array
formula (`cm` in the file) spills as far as its result goes; the cells the file kept for its saved result are not cells of the model, the spill
is. One it cannot evaluate keeps its saved result cells as plain values and the formula as cached-only. So does a legacy one the engine evaluates
to something other than what the file saved: the engine's result is compared with the results the file holds for the range after the load, and
where a saved member differs (`{=ROW(A1:A3)}` over three cells saved as 1, 2, 3, which the engine evaluates as one value, 1, repeated), or the
engine has no result over the range (an error, a cell in the way), the anchor and the members stay as the file had them, the formula is
cached-only (its saved results are never recalculated) and it is counted in `xlsx.formulas.cachedOnly` like a formula the engine does not have. With `recalculateOnLoad` the formulas that read such a range are evaluated again from the saved results, so they agree with what the range shows; without it they keep their saved results. A dynamic array (`cm="1"`) is not compared: the engine's spill replaces the cells the file saved (a file that never calculated, such as one from xlsxwriter, saves a 0 and no spill).
A saved result the file does not give (no cell for a member) is not held against the engine, a blank source cell inside a legacy array's result is 0, as Excel shows it (the same result as a saved 0 and only that: a saved empty string or `false` is a different one, so the array keeps the file's values), numbers are held to a relative 1e-9 and a text `"1"` is not the number 1 (the file's value is kept when in doubt), and one the engine reproduces (the same values, a
scalar filled across the range included) stays evaluated. A one-cell array formula stays an
array formula. Known divergence: a dynamic array's spill still shows a blank source cell as blank where Excel shows 0 (`=C2&"x"` on it gives `"x"`, Excel `"0x"`); the engine's spill semantics are unchanged here (sheets TODO). On export an array formula is written with `t="array"` and its range (the engine's spill region for one that spills, the file's
extent for a cached-only one), the spilled values are written as the plain values Excel keeps next to the formula, and a dynamic array also
gets the cell metadata Excel marks it with (`cm` and `xl/metadata.xml`); a legacy (CSE) array formula stays legacy on export, written without `cm`, even when the engine spills it (Excel shows it as `{=...}` again, not as a spilled formula), and a formula typed in the editor that spills is written as a dynamic array. A dynamic array whose saved extent is one cell is kept as its saved
value until a cell it refers to changes. The cells an array formula covers cost as much to take on load as they are many, so a sheet is
limited to 1,000,000 cells of array formulas (the `maxArrayCells` option of `importFromXlsx` and `importWorkbookFile`, the `maxArrayCells` prop of `WorkbookCanvas`; a dynamic one costs at most the sheet's cell count): past it the
formula is kept as cached-only (one cell with its saved result, the extent unchanged in the file) and reported as `xlsx.package.sizeLimit`
(`array formula(s) kept as saved values`, the effect names the limit and the option). The export has a cap of its own: a result the engine spilled over
1,000,000 cells (the `maxArrayCells` option of `exportToXlsx`) is written as its first rows only, the formula's range cut to match (Excel recalculates
it and spills it in full), and each one is reported to the `onWarning` callback of the export (in the React editor the `onExportWarning` prop of `WorkbookCanvas`, and the `onWarning` option of `exportWorkbookFile`; the editor shows no notice of its own, so a host that wants its users told shows the message; the first 20 one by one, then one message with the count of the others). The cap is per result, so the export also has a budget for the whole workbook, `maxTotalArrayCells` (default 1,000,000 cells of array formula results over all formulas and sheets): once it is used up, the next results are cut the same way, so many results just under the cap cannot add up to more (each result that is cut still keeps one cell, its anchor, so the file can hold a few cells more than the budget). Which results are cut does not depend on the order the cells were entered in: the export takes the formulas sheet by sheet in the workbook's order, and in each sheet row by row, left to right, so the results nearest the top left of the first sheet are kept whole and the budget runs out on the last ones. An error value in a result is written as an error cell (`t="e"`), not as text, and so is an error saved with a legacy array's members; finding those saved errors is bounded by the same `maxTotalArrayCells` budget (the members of the ranges the export has looked at), so past it they stay the text of the error. Measured in a child process (Node 24, a 1 GB heap),
a file of 1.7 KB with `ref="A1:J400000"` (4 million cells) now imports in 0.2 s as a saved value and exports in 15 ms; a range of exactly 1,000,000
cells (`A1:J100000`) imports in 1.1 s and exports in 8.9 s (a 2 MB file); a 2,000,000 cell range a host lets through takes 2.4 s to import and 7.7 s to
export (written as 1,000,000 cells, 2 GB heap). Before the limit, `A1:J400000` took 5 s and 955 MB to import and 44 s and 3 GB to export.

**Legacy formulas and `@`.** A formula saved without the array or dynamic-array mark is a legacy one: where it uses a range of several cells as an operand of its
own operators (`A1:A3*2`, `-A1:A3`, `A1:A3&"x"`, `Sheet2!A:A*2`, in a shared formula too) Excel intersects the range with the formula's row or column (`#VALUE!` outside it). The import
shows and evaluates that with the `@` Excel 365 shows (`=@A1:A3*2`) and the export writes it back **as the file had it, the bare range** (`A1:A3*2`, never
`_xlfn.SINGLE(A1:A3)*2`, which Excel 2016 and earlier read as `#NAME?`): in a formula without the array mark Excel applies the same intersection to a bare range operand, so the file means
the same in Excel 2016, 365 and LibreOffice and a plain open and save does not change the text. The rule is an `@` directly before a multi-cell range operand outside every call and group,
in a formula that is written without `t="array"` and `cm`. Every other `@` keeps `_xlfn.SINGLE(...)` (before a call, a name, a spill reference or inside a call, where a bare range would not mean the same, and in
a dynamic-array formula, where a bare range would spill); a formula typed in the editor with `@A1:A3` is written bare in the same way. One difference from the source text: a file that already
had `_xlfn.SINGLE(A1:A3)` over a range operand in a formula without the array mark (written by Excel 365 for a typed `@`) is written back as the bare range, which means the same. **Known divergence** (sheets TODO): the engine does not
intersect a range inside a call's arguments, so in a legacy formula `SUM(A1:A3*2)` sums the array (Excel intersects the range and gives the cell's double or `#VALUE!`), `LEN(A1:A3)` gives 5 and
`IF(A1:A3>1,1,0)` gives 1 where Excel gives `#VALUE!` outside the range's rows (the cell's result inside them), and `ABS(A1:A3)` is `#VALUE!` where Excel gives the intersected cell's absolute value inside the range's rows. The saved
results are kept unless the workbook is recalculated on load. A name or a structured reference is not intersected either.

A formula whose genuine text result equals an error literal (`="#N/A"`) is written as an error value (`t="e"`): the model keeps a result as a
value and cannot tell the text `#N/A` from the error, so the two are the same on export.

**Cell model.** A cell's JSON gains the optional `cachedOnly: true` and `arraySpan: { rows, cols, spill? }` (collab schema version 2, see
`documentation/collaboration.md`).

The XLSX loss counts grow with each fidelity change that keeps a construct: a feature that becomes preserved leaves the table or changes state. The package ledger
in `fixtures/xlsx/` maps every part of a file to a mapped, dropped or unaccounted status using these ids.

`inspectDocx(bytes)` / `detectDocxLoss(bytes)` return the table above (the report the confirmation dialog uses). Pass `{ detail: 'full' }` for the
complete measurement, which adds ids for things the importer flattens or ignores rather than drops: `docx.listFormatting` (other number formats) and `docx.sectionProperties` (chapter numbers in page numbers), and a `where` breakdown by field kind on
`docx.fields`. The full report also lists a long tail: `docx.formattingRevisions` (`rPrChange` of a paragraph mark, `tblPrChange`, `trPrChange`, `tcPrChange`,
`sectPrChange`), `docx.dropCaps`, `docx.watermarks`, `docx.pageBorders`, `docx.lineNumbers`, `docx.hyphenation`, `docx.tabStops` (custom stops and
leaders), `docx.rtl`, `docx.ruby` (base text kept, reading marks lost), `docx.embeddedFonts`, `docx.altChunk` and `docx.legacyForms` (`FORMTEXT`/`FORMCHECKBOX`/`FORMDROPDOWN`, whose displayed text is kept as plain text; they are no longer also counted in `docx.fields`). In both modes `docx.charts` counts chart and SmartArt objects referenced from the body (not the XML parts behind them) and
`docx.floatingImages` counts anchored pictures only; anchored shapes and text boxes are not floating images. Tabs, line breaks, soft and non-breaking hyphens, and the text inside smart tags, custom XML and ruby base text are imported, so they are no longer reported as lost. The DOCX fidelity harness (`fixtures/docx/`) records the full report.

Tracked changes: `w:ins` and `w:del` around runs and links are kept as the `insertion` and `deletion` marks (author, date, id), with the deleted text kept (`w:delText`), shown struck through, and written back as `w:ins` / `w:del`. They are not applied on import, so a document with deletions has more text than it did before. A change around a field is not kept as a change (an inserted field stays as it is, a deleted field is dropped), a deleted image or note reference is dropped and an inserted one stays as ordinary content; each adds a warning and is counted as `docx.trackedChangesNotKept` (changes around a field, image or note reference, and deleted text inside a field result). Headers and footers keep no tracked changes (deleted text is dropped, inserted text kept as ordinary text: `docx.trackedHeaderFooterChanges`, which also counts a formatting change there), and a change around whole paragraphs or tables is counted as `docx.trackedBlockChanges` (its content is not imported). Moves are kept as a deletion and an insertion that share the name of the move, formatting changes of runs and paragraphs (`w:rPrChange`, `w:pPrChange`) with the formatting before, and inserted or deleted paragraph marks and table rows as attributes of the paragraph or row. What stays in the loss report: `docx.formattingRevisions` (the change of a paragraph mark's own formatting, a paragraph change of numbering, tab stops, borders or shading, whose old value the change cannot carry, and changes of tables, table rows, cells and sections: `tblPrChange`, `trPrChange`, `tcPrChange`, `sectPrChange`), `docx.trackedBlockChanges`, `docx.trackedStructureChanges` (a tracked change of the paragraph mark of a paragraph that is read as a page break or a horizontal rule, which have no place for it; an image paragraph keeps its change as a paragraph with an inline image) and `docx.trackedHeaderFooterChanges`; a change in a field's result is not kept, and a formatting change on a run with no text of its own (a field result, an image, a note reference) is not kept either; each adds a warning instead of a count. A table cell of one paragraph keeps that paragraph's block (not just its text) when the paragraph has a tracked change of its mark, so the change is read and written back like any other. In the file, the change of a paragraph mark and the changes of its text can share one `w:id`; they are read as separate changes (one per kind) and written with ids of their own. A move of a paragraph mark is written back as an insertion or deletion.

Paragraph and run properties the importer keeps (line spacing, left/right/first-line/hanging indents, keep-with-next, keep-lines-together, page-break-before, all caps, hidden text, East Asian and complex-script fonts, list start numbers and restarts) are not reported as lost. The editor does not lay out keep-with-next, keep-lines-together, page-break-before or at-least/exact line heights yet, and shows hidden text dimmed instead of removing it; all of them are kept in the document and written back on export.

Named styles are kept: the names, ids and own properties of the paragraph and character styles the document uses (with the styles they are based on, linked to or followed by) are stored in `DocumentData.namedStyles`, blocks and runs keep a `namedStyleId`, and the export writes them back into `styles.xml` with `pStyle`/`rStyle` references, so `docx.namedStyles` is no longer reported. The editor does not show a style gallery yet; the formatting of a styled paragraph or run is also applied directly to it, as before. Table styles are kept as well (see below). The style definitions of styles nothing uses are not kept.

Fields are kept with their cached result: `REF`, `PAGEREF`, `SEQ`, `STYLEREF`, `DATE`, `TIME`, `TITLE`, `AUTHOR`, `IF`, `MERGEFIELD` and the other kinds are imported as a generic field (instruction, kind and the result Word last computed, with its formatting), shown as that result and written back as a field so Word can refresh it. They are never recalculated in the editor, so a stale `DATE` or `PAGEREF` stays stale until Word updates it. `HYPERLINK` fields become links, and a field inside another field's result is part of that result. `docx.fields` now counts only what is not kept as a field: an index (and a table of contents that cannot be read as a block) keeps its text as static paragraphs. Two cases are still reported as warnings: fields in headers and footers other than `PAGE`/`NUMPAGES` (a single cached value would be wrong on most pages) and a field nested in another field's instruction (`IF { PAGE } > 1 ...`), which is kept as its cached value. A field whose result spans several paragraphs (other than a table of contents or index) keeps its text only.

Table formatting is kept: borders (line style, width and colour, per table and per cell), cell shading, vertical alignment, repeating header rows, `cantSplit`, column widths and the table style (with its `tblLook`) are imported and written back, so `docx.tableFormatting` is no longer reported. A table style's conditional formatting (header and total rows, first and last column, banding, corner cells) is applied to the cells it reaches, the way Word resolves it: shading, borders and vertical alignment become the cell's own, text properties (bold, colour...) become the formatting of its runs, and the table style itself is kept in `namedStyles` and written to `styles.xml`. Known limits: a table style's paragraph properties (spacing, alignment) and cell margins are not applied; the table's overall width, indentation and alignment are not kept (columns use the grid widths); the editor does not split tables across pages, so repeating header rows and `cantSplit` are stored and exported but not acted on; other line styles (wavy, 3D, art borders) are approximated by single, double, dashed or dotted; pattern shadings (`w:val` other than `clear`/`solid`) keep only their fill colour. A table with no border lines is stored with empty `borders` and shows no lines.

Table structure is kept: a cell's paragraphs, lists, headings, images and nested tables are imported (`DocTableCell.blocks`) and written back, so `docx.tableStructure` is no longer reported. A vertical merge ends in a row that does not continue it, a continuation cell with no merge above it stays an ordinary cell, and a row that starts after skipped grid columns (`w:gridBefore`) gets an empty cell without lines in front. A cell's paragraph formatting is kept when the cell has several blocks; a cell of one paragraph keeps its text and run formatting only (and its block when the paragraph has a tracked change). Known limits: a table nested more than 20 deep is dropped with a warning; a rotated cell (`w:textDirection`) is kept and exported but shown with horizontal text; the editor draws every paragraph of a cell without space between paragraphs; the table style's paragraph properties are not applied (see table formatting above).

Headers, footers and section properties are kept in the model and written back, so `docx.headerFooterVariants` is no longer reported and `docx.sectionProperties` only counts chapter numbers in page numbers: each section's default, first-page (`w:titlePg`) and even-page header and footer (by `w:type`, with the document's even/odd setting) are imported, as are the page number restart and format (`w:pgNumType`), vertical alignment (`w:vAlign`) and text columns (`w:cols`: count, spacing, separator, unequal widths). A first-page or even-page variant that is switched on without a part of its own stays empty and is not written; a section with no header or footer reference has none (Word would repeat the previous section's, and does so again when the file is written back). The editor draws the first-page header and footer only: even-page headers and footers, page number restarts and formats, vertical alignment and columns are stored and exported but not shown (`docx.columns` keeps counting multi-column sections: they are laid out as one column). Header and footer fields other than page numbers are still dropped with a warning, and tables in headers and footers are not imported.

Bookmarks and internal links are kept: a `w:bookmarkStart` becomes a named position in the text (including `_Toc` and `_Ref` bookmarks; Word's `_GoBack` cursor marker is dropped), a `w:hyperlink` with an anchor becomes a link to `#name` (`url#name` when it has a target as well), and clicking such a link in the editor scrolls to the bookmark. A bookmark that covers text is kept as a point at its start, so its range is not preserved: a `REF` field the application that opens the exported file recalculates would then show nothing, though its cached text is kept and `PAGEREF` is unaffected. A bookmark that starts between paragraphs moves to the start of the next paragraph, and bookmarks in headers and footers are dropped. A link around a field (a table-of-contents page number) keeps the field but not the link. There is no `docx.bookmarks` id any more.

### PPTX loss ids

`detectPptxLoss(bytes, { detail })` (`@b32nio/spindle-io/pptx`) parses the package XML with the same safety measures as the XLSX detector (entities are
never expanded and a DOCTYPE is cut out, nesting is capped at 100 levels, a part is read only up to 64 MB and the whole read up to 256 MB, counted on
the bytes that actually come out of the zip so a forged header cannot make a bomb inflate, a package of more than 50,000 entries is not scanned, nothing
throws). **The editor cannot open a presentation yet** (plan K9 to K15: the io reader `importPptx` reads the package, presentation, theme, slide list, text, shapes, pictures, tables, hyperlinks, groups, connectors, custom geometry, speaker notes, comments, layouts and fonts so far; the editor's `importFromPptx` and dialog follow), so the effect of an id the reader does not read yet still says
`lost: not imported (the PPTX reader does not read this yet)` (a few say more: macros are never run or kept, an encrypted package
cannot be opened). Ids the reader already reads say `kept: ...` or `approximated: ...` (charts, SmartArt, OLE objects and controls, audio and video, ink, transitions and animations, which the reader keeps as they are (plan K11, below), groups and connectors, custom geometry paths, speaker notes, notes masters, picture crops, SVG fallbacks, merged and styled table cells, hyperlinks, hidden slides, slide size, run languages, fonts, layout inheritance, colour maps, font schemes, autofit, bullets, tab stops, columns, vertical and right-to-left text, fields, character spacing, baseline, custom and unsupported geometry, gradient and pattern fills). The ids are stable; as importer PRs land, only counts, effect texts and states change. The default `detail: 'summary'` returns the
16 summary ids; `'full'` adds the finer ids and is what `npm run slides:pptx-fidelity` records. `where` lists slides as `Slide n` (their place in the
presentation; a slide part the presentation does not list is named by its file), or the fonts, geometries, languages, link schemes or action kinds
named in the id's row below, capped at five entries.

Counts are of objects, not of package parts, and are taken from the **slides** (nothing on a layout or master is counted; those carry only the
masters, theme, colour map and font ids): a chart is one chart however many parts it has, an `mc:Choice`/`mc:Fallback` pair is read once (the
fallback is skipped), a slide with a transition counts once however the transition is written.

Slides can now hold gradient, picture and pattern fills (plan K1: shapes, text boxes, table cells and backgrounds; a pattern is kept in the model but painted as a solid blend of its two colours, so it is approximated, not exact). Nothing imports a `.pptx` yet, so `pptx.shapes.gradientFill` and `.patternFill` still report `lost: not imported`; their state changes when the reader (K9) maps these fills.

Pictures can now be cropped (plan K2: `ImageElement.crop`, the percent of the source trimmed from each edge, the same quantity as `a:srcRect`; the fit applies to the cropped region). The reader maps `a:srcRect` to it (plan K10a), so `pptx.images.crop` reports `kept`. Negative `srcRect` values (padding outside the picture) have no model equivalent and are clamped to zero.

The reader reads pictures and tables (plan K10a). A `p:pic` becomes a picture with its embedded image as a data URL (the type is taken from the bytes, not the extension; an SVG with a PNG fallback reads as the PNG), its crop, frame, rotation and flips and outline. EMF and WMF have no browser renderer and a linked picture is never fetched: both become a labelled placeholder with the frame and alternative text (`pptx.images.unsupportedFormat`, `.linked`; the image data of an EMF or WMF is not kept yet, which K11's opaque elements will change). A table keeps its spans, per-cell borders, margins and anchors, with the table style of `ppt/tableStyles.xml` resolved into each cell (whole table, banding, first and last row and column; corner cells and a style the file does not define are not applied, and a `tint` becomes the matching lighter variant). Hyperlinks on runs, shapes and pictures keep only `http`, `https`, `mailto` and `tel` addresses; `ppaction://` and `file:` targets are kept inert (`pptx.actions`) and any other scheme is dropped with a warning. Pictures and tables inside groups are read with the group reader (K10b, next paragraph).

The reader reads groups, connectors and custom geometry (plan K10b). A `p:grpSp` becomes a group whose `children` have their frames **composed** into slide space (the group's `a:chOff` and `a:chExt` scale, rotation and flips, through every group it sits in; the composition is `composeGroupChain`, shared with slides-core), and a `grpFill` shape takes the fill of its group. A `p:cxnSp` connector keeps its route (`straightConnector1`, `bentConnector*`, `curvedConnector*` with their adjustments), its outline and arrow heads and the shapes its ends are glued to (`stCxn`, `endCxn`: shape id and site index). `a:custGeom` keeps its paths (move, line, cubic and quadratic curves, arcs, close, several paths, fill modes); guide formulas are not evaluated, so a path that uses one (or is malformed or too large) keeps the shape's frame, fill and text but not its outline (`pptx.shapes.custGeom`, `.unsupportedGeometry`). Groups nested more than 64 levels are dropped with a warning. `pptx.shapes.groups.nested` and `.connectors.elbowCurved` report `kept`. The outer shadow of a plain shape is kept (plan K6 and K13: `PptxShape.shadow` with colour, alpha, blur, distance, direction and anchor, read from an `a:effectLst` that holds exactly one `a:outerShdw`, written back by `exportPptx`). Every other effect (glow, reflection, soft edges, inner and preset shadows, a second shadow, the shadow of a group, picture, connector or run) is still dropped, and `pptx.shapes.effects` reports it as `lost`; it no longer counts a shape whose effect list is only the outer shadow the reader keeps.

The reader reads speaker notes and comments (plan K10c). The body placeholder of a slide's notes page becomes `PptxSlide.notes`, a text body with the run and paragraph formatting of the notes (bold, italic, underline, colour, size, bullets, numbering, spacing, links), its styles inherited from the **notes master** (`p:notesStyle`, then the master's body placeholder and colour map); the rest of the notes page (slide image, header, footer, date, page number, other shapes) and the notes master's own layout and theme are not kept. Comments become `PptxSlide.threads`, one `PptxCommentThread` per comment with its replies (root first): the legacy format (`ppt/commentAuthors.xml`, `p:cm` with its position in px, replies as `cm`s whose `p15:parentCm` names the comment they answer; a reply joins the thread of the comment it answers wherever that comment is in the part, a reply to a reply joins the thread at the top, and a reply whose parent is missing, or whose parents loop, stays a thread of its own) and the modern format (`ppt/authors.xml`, `p188:cm` with `p188:reply`s and a `status`, `resolved` and `closed` reading as resolved; the anchor is the slide, or the shape a `*MkLst` marks, when the slide holds a shape with that id). Comment text is plain text and times are UTC ISO-8601 (a time with no zone is read as UTC); an author the list does not name is `Unknown author`; at most 10,000 comments (threads and replies together) per slide are read, with a warning for the rest; notes or comments of a slide that cannot be read are dropped with a warning and the rest of the slide is kept. Anything a mention or a text range inside a modern comment points at is kept only as the plain text. **`pptx.comments` is reported only for a comments part no slide points at** (`lost`: comments are read through their slide; the comments of a slide are kept), and `pptx.notes` is narrowed to notes with formatting in the notes body placeholders (`approximated`; bold in a footer or header placeholder does not count; a notes page no slide points at is not read, and is reported only when its body is formatted); `pptx.masters.notesMaster` is `approximated`. The text parity check covers the notes body runs.

Text bodies can now hold the body-level attributes of `a:bodyPr` (plan K3a: per-side insets, `anchorCtr`, `normAutofit` with its `fontScale` and `lnSpcReduction` applied as stored, `spAutoFit` as resize, `vert` and `eaVert`, `numCol`/`spcCol`). Nothing imports a `.pptx` yet, so `pptx.text.autofit`, `.vertical` and `.columns` still report `lost: not imported`; their state changes when the reader (K9) maps them. Known limits: PowerPoint's own line breaking differs from the browser's (fonts and metrics), so a stored scale can leave slightly more or less room than in PowerPoint; shrink-to-fit with several columns measures the balanced height; `resize` leaves vertical text and shapes alone (a shape keeps the imported `spAutoFit` but does not grow). Paragraph bullets, spacing forms, tab stops, baseline, caps, character spacing and fields (`pptx.text.bullets.*`, `.tabStops`, `.spacing`, `.baseline`, `.fields`) are not part of this step.

Paragraphs can now hold the attributes of `a:pPr` (plan K3b: `buNone`/`buChar`/`buAutoNum` with `buClr` and `buSzPct`, `startAt`, `lnSpc` as a multiple or exact size, `spcBef`/`spcAft` in points or percent, `marL`, `indent`, `tabLst`; `flattenLevelStyles` bakes a level's `lvlNpPr` defaults into the paragraphs). Nothing imports a `.pptx` yet, so `pptx.text.bullets.custom`, `.tabStops` and `.spacing` still report `lost: not imported`; their state changes when the reader (K9) maps them. Known limits: tab stops are kept and synced but the editor lays out default tabs; picture bullets (`buBlip`) and bullet fonts (`buFont`) are not modelled; the number scheme set is arabic, alpha and roman (other `buAutoNum` types fall back to arabic); a paragraph's bullet size and colour follow the first-run defaults only when set explicitly; the editor numbers by list run, not by indent level. 

Runs can now hold the attributes of `a:rPr` that K3c adds (`baseline`, `cap`, `spc`, `lang`) and `a:fld` runs of type `slidenum` and `datetime*` (plan K3c: marks `baseline`, `caps`, `charSpacing`, `lang` and the inline `field` node, whose cached text keeps its formatting). Nothing imports a `.pptx` yet, so `pptx.text.baseline`, `.spacing`, `.lang` and `.fields` still report `lost: not imported`; their state changes when the reader (K9) maps them. Known limits: a raised or lowered run is drawn at 65 percent of its size shifted by the stored percent (PowerPoint's exact size change differs by font); `cap="small"` uses the browser's small caps; the editor shows a field's stored text (a slide number reads `‹#›`) while the idle slide shows the live value; a date field shows the current date in the viewer's locale, not the format code of the file (`datetime1` to `datetime13` map to three layouts); the language tag is stored and exposed as `lang` on the run but does not drive spell checking; a tag with a one-character subtag (an extension such as `de-u-co-phonebk` or private use such as `en-x-foo`) is not stored.

Content controls are kept: a `w:sdt` of type rich text, plain text, drop-down list, combo box, date, check box, picture or building block is imported as a wrapper (`content-control` block, or `contentControl` inline content) around its content, with its title (`w:alias`), tag, lock, placeholder, list items, date format and value, and check box state, nested to any depth, and written back as a `w:sdt`. `docx.contentControls` now counts only what is still lost, with the reason in `where`: repeating sections and their items, data-bound controls (custom XML parts are not read), equation, citation, bibliography and group controls, controls around table rows or cells, and a control around a section break; all of these import as their content only. Known limits: the editor shows a title chip and a tooltip and toggles check boxes, but has no date, list or picture pickers, and the lock is kept and exported but not enforced; the placeholder text lives in the file's glossary part, which is not kept, so a control showing its placeholder keeps the text it displays; a control inside a field's result, in a header or footer, or around a section break is read as its content; custom check box glyphs (`w14:checkedState`) are written back as Word's default ones; `w:id`, `w:temporary` and other properties are not kept (ids are renumbered). Legacy form fields keep the text they display as plain text, and are still reported as `docx.legacyForms`.

Footnotes and endnotes are kept: each reference in the body becomes a note reference holding the text of its note (with its formatting, links, line breaks and fields), shown in the editor as a superscript number with each footnote at the bottom of its page (endnotes collected at the end of the section), and written back to `footnotes.xml` / `endnotes.xml` (with Word's separator notes and the settings that point at them), so `docx.footnotes` and `docx.endnotes` count only notes that nothing in the body refers to, notes whose only reference is in a text box, and notes in a part that cannot be read. Known limits: a note of several paragraphs becomes one paragraph with line breaks, and a table in a note is not kept (a warning); a picture in a note is kept but a list is just its text; a reference in a header, footer, field result or note is not kept (a warning); notes are numbered by the editor (footnotes 1, 2, 3, endnotes i, ii, iii, Word's defaults; the number format, restart and position settings of the file are not read) and the number Word shows after opening the written file is Word's own; notes can be inserted (Footnote menu) and edited in place in the editor; footnotes are laid out at the bottom of their page by the editor's own layout, which can break pages differently from Word (a page gives at most half its height to notes, and a note that does not fit continues on the next page); the note styles (`FootnoteText` and the reference styles) are not written, the formatting is on the runs.

A table of contents is kept as a `toc` block: a `TOC` field that starts in the first entry paragraph and ends after the last (in the body, or in a content control such as Word's Table of Contents building block) is read with its entries as they were saved (links to the `_Toc` bookmarks, tabs, `PAGEREF` fields with their cached numbers, entry styles), shown with a dotted leader and the number at the right, never recomputed on open, and written back as the field (begin, instruction and separator in the first entry, a right tab with a dotted leader at the margin on each entry, the end in a paragraph of its own) so Word can refresh it. An entry made in the editor is written with its number as a `PAGEREF` field. `docx.fields` now counts only a table of contents that stays static text (its field ends elsewhere than the body or control it starts in, has a table or section break inside, or is a simple field `w:fldSimple`) and indexes. Known limits: the entries are plain paragraphs (a heading or list style on an entry is not kept as such), the title paragraph Word puts before the table ("Contents") is an ordinary paragraph, a table of contents in a table cell, a header or a footer is static text, and the tab stops of the entries are not kept (the editor draws a leader at the margin; the export writes one at the margin too).

Comments are imported (threads, replies, resolved state and anchors), so `docx.comments` is reported only when the comments part itself is damaged and its comments cannot be read.

Parse-time problems found while importing (an unresolvable image, an unsupported field…) still arrive as `warnings`.

## Files that cannot be opened at all

The importers do not report these as loss: they refuse the file, with an `ImportError` (`@b32nio/spindle-io`) whose `code` hosts can switch on and
whose `message` is fit to show a user. `importXlsx` and `importDocx` throw nothing else. A forged or corrupt zip entry (including the `mimetype` marker) is `corrupt`, never a plain `Error`.
A CSV over the size limit (`importFromCSV`, `importWorkbookFile`) is refused with an error of the same shape (`name` `ImportError`, `code` `size-limit`) that is
not an instance of the `@b32nio/spindle-io` class, because the CSV path is synchronous and does not load that package; `isImportError(e)`
(`@b32nio/spindle-sheets-core`) recognises both, so a host handles every refusal in one place. The loss ids above (`xlsx.package.encrypted`, `.legacyBinary`, `.sizeLimit`) are
what the `full` detail level reports for the same files, so a host that inspects first can say the same thing before trying.

| `code` | When |
|---|---|
| `encrypted` | an OLE compound file with an `EncryptedPackage` or `EncryptionInfo` stream (password to open), or a zip entry marked encrypted |
| `legacy-binary` | any other OLE compound file (`.xls`, `.ppt`, `.doc`), or a binary workbook (`.xlsb`) |
| `not-a-package` | empty, not a zip, an OpenDocument or Apple iWork package, or a zip without `[Content_Types].xml` |
| `size-limit` | over a limit below |
| `corrupt` | truncated or damaged zip, a part that cannot be inflated, a part name that is unsafe (`..`, absolute, backslash, drive letter, NUL), or a reader failure on a well-formed package |

Limits (options on the importer, `limits`; defaults `DEFAULT_IMPORT_LIMITS`): package 100 MB, 20,000 entries, 1 GB uncompressed in total, 500 MB per part
(256 MB for an XML part), compression ratio 200:1. The ratio is only judged for a part (or package) that inflates to more than 16 MB: smaller parts cannot cost more
than that however well they compress, and legitimate files do contain tiny, very regular parts. The limits are checked from the zip's declared sizes first and then
again while each part is inflated, so a header that lies about a size cannot get a bomb inflated.
For XLSX, more limits bound what the sheets of one workbook can cost: `maxSheetFormulaChars` (32 Mi) and `maxFormulaChars` (64 Mi, all sheets together) bound the formula text gained by expanding shared formulas (a formula costs its length plus 16): past them the remaining cells keep their saved value and lose the formula, with one warning for the sheet. A formula over 8192 characters (Excel's own limit) is dropped the same way. `maxTotalCells` (5,000,000, five times the 100,000 x 10 performance file) and `maxSheets` (1,000) cut a workbook off, with one warning, after the sheet that passes them; the workbook's `<sheet>` entries read are capped at four times `maxSheets` (chart sheets, repeats of a part and sheets without a part count as entries), with one warning. `maxRanges` (1,048,576) is the budget of merged ranges and hyperlinks over all the sheets of a package; each sheet also reads at most 1,048,576 merges and 65,530 hyperlinks (Excel's own limit), and what is past a limit is left out with one counted warning. A worksheet part is read once: a second `<sheet>` naming it is skipped. Warnings about single items (a hyperlink whose relationship is missing, a repeated sheet or sheet name, a comment part that is not in the package) are given in full for the first 20 of a kind and then counted in one message. The small elements of a sheet read as trees (`sheetPr`, `dimension`, `sheetViews`, `sheetFormatPr`) are left out, with a warning, past 64 KiB each, and the raw `extLst` past 8 MiB. Memory, as measured for the reader alone (Node 24, a 4 GB heap): about 0.17 GB of process memory (RSS) per million cells of plain numbers; 5,000,000 cells took 0.86 GB (numbers), 1.04 GB (shared strings), 1.22 GB (formulas) and 1.0 GB (with 1,048,576 merges, as the cells exist before the merged ones are dropped) in the shapes measured for this reader, and up to 2.0 GB in the review's variants (1.67 GB of formulas, 1.82 GB of shared strings, 1.96 GB of merges, measured before the strings were copied): plan for 2 GB. A host that also builds the editor's own model from the result (a second copy of every cell), and any browser host (a tab is commonly limited to 2 to 4 GB), should lower `maxTotalCells`; 1,000,000 keeps the 100,000 x 10 file whole at a fifth of the cost. The workbook-level parts are bounded by what they keep, not by their size: the shared strings, the relationships and the content types are read as events (memory is the strings and entries kept; at most `maxTotalCells` strings, as no cell could name more, and `maxPartElements` rich-text runs, past which a string keeps its text and loses its fonts), and the styles, theme and workbook are element trees built under an element budget, `maxPartElements` (1,000,000: Excel's 64,000 cell formats and as many differential formats make about 200,000 elements, so a sound file is five times under it). A tree part over it is not read at all (one warning, and its readers give their defaults; the workbook part is read in one pass, with its defined names as a list capped at the same number, so a workbook of a million names is read, with one warning for the names past the cap, and one whose other elements are over the budget is refused as corrupt with an error that says it has too many elements and names the limit), a relationships or content-types part keeps its first entries; a tree costs about 420 bytes per element, so a part is at most about 420 MB however long it is. `maxRows` (2,097,152, two full worksheets) bounds the rows that carry their own settings (height, hidden, style, outline) over the package, with one warning per sheet past it; a row with none costs nothing. Entity-dense text is decoded in 64 KiB windows, so its cost is the text and not several times it. A sheet name is cut at 255 characters (Excel allows 31) with a warning, and a warning quotes the file's own text (sheet name, cell value, address, relationship id, part name) at 64 characters. The hostile shapes of the review (five million shared strings, a million borders, fills, fonts or theme colours, 400,000 rich runs, a million relationships, defined names or content-type overrides, 100 MB of entity-dense text, eight sheets of 1,048,576 rows without cells, a 10 MB sheet name, a million-digit value) are imported in a child process with a limited heap by `hostile-memory.test.ts`. These are options of the io entry (`importXlsx`) and of `importFromXlsx`; the deprecated `importXlsx(bytes)` wrapper of `@b32nio/spindle-shared/export/xlsx` forwards no options.

XML is parsed with entities never expanded, the DOCTYPE removed and nesting capped at 256.

- **DOCX:** the five predefined entities are still decoded; a declared one (`&lol9;`, an external entity) stays as written text. `importDocx(bytes, { limits })` and `detectDocxLoss(bytes, { limits })` take the same options. The detector reads nothing from a package over the limits (an empty report; the import then says why). A `.docx` without `[Content_Types].xml` is `not-a-package`.
- **Known gap:** docs-core `importFromDocx` does not forward `limits` yet, so hosts using that entry point get the defaults only (follow-up in docs-core, tracked in `documentation/docs/TODO.md`).
- **CSV:** a leading byte order mark is dropped, text over 100 MB is refused (`code` `size-limit`).

### What the import limits cut

A limit that cuts something is not only a warning string: the importer counts each cut by kind and `importFromXlsx` appends the items to the `loss` it returns (and `importXlsx` returns them as `limitLoss`), with the id `xlsx.package.sizeLimit`, a label that says what was left out, a `count`, the first sheets or parts it happened in (`where`), and an `effect` that starts with `lost:` or `approximated:` and names the limit, its value and the option that raises it. An item is there only when something was cut. These limits are options of `importXlsx` and `importFromXlsx` (`limits`), defaults in `DEFAULT_IMPORT_LIMITS`:

| Limit | Default | What it bounds | Loss item (label) |
|---|---|---|---|
| `maxTotalCells` | 5,000,000 | cells kept over all sheets; a sheet that is cut keeps what fits, a later sheet with anything to cut is not kept (an empty one is) | sheet(s) cut at the cell limit |
| `maxScannedElements` | 16,777,216 | cell, row and column elements scanned over all sheets, kept or not (about 15 s) | sheet(s) cut at the scan limit |
| `maxSheets` | 1,000 | worksheets read (the entries are read to four times that) | worksheet(s) not read |
| `maxRows` | 2,097,152 | rows with their own settings (height, hidden, style, outline) | row(s) with settings left out |
| `maxRanges` | 1,048,576 | merged ranges and hyperlinks (also 1,048,576 merges and 65,530 links per sheet) | merged range(s) and hyperlink(s) left out |
| `maxColumns` | 1,048,576 | `<col>` ranges read (16,384 per sheet) and the columns they set up to a sheet's last cell | column setting(s) left out |
| `maxExtensionChars` | 64 Mi characters | raw `extLst` text kept (8 Mi per sheet) | extension list(s) not kept |
| `maxSheetFormulaChars`, `maxFormulaChars` | 32 Mi, 64 Mi | expanded shared-formula text (a formula over 8192 characters is dropped too) | formula(s) not imported (approximated: the value is kept) |
| `maxPartElements` | 1,000,000 | elements of a workbook-level part, entries of a relationships or content-types part, rich-text runs, defined names | part(s) over the element limit, part(s) of the shared strings not read, defined name(s) not kept |
| `maxRelationships` | 1,048,576 | relationship entries read over the whole package (only the kinds the reader uses are kept) | part(s) with relationships not read |

Not limits of the options but cut and counted the same way: a sheet name over 255 characters (approximated), a small sheet element (`sheetPr`, `dimension`, `sheetViews`, `sheetFormatPr`) over 64 KiB, and a number format code over 255 characters (kept as written, not read as a date or time; approximated). Every limit cut also has one warning in `warnings`, the first of its kind for those that can repeat on every sheet.

An element with more than 1,024 attributes (namespace declarations included; Excel writes fewer than 30) is damage like a stray end tag: the sheet is read as far as it, a workbook-level part is skipped with a warning, and a workbook part is refused as corrupt. Without a cap, a few MB of zip can ask the engine for an object of eight million properties, which it does not finish. Merged ranges are applied to the model in one pass per sheet (`WorkbookImpl.mergeCellsBulk`, the same result as `mergeCells` one by one, without the undo steps a load must not leave); merges that overlap (Excel writes none, and repairs a file that has them) are resolved as one by one would resolve them (the later wins), in O(n log^2 n), however many: 100,000 blocks with one overlap lose only the two they overlap, and 200,000 merges that each overlap the next are decided in a few seconds.

**What the limits bound, and what they do not.** The reader is bounded; loading the result into the editor's model is not, for huge formula counts. Measured through `importFromXlsx` into a `WorkbookImpl` (Node 24), where the reader itself took 0.1 to 0.2 s of each: 20,000 array formulas (`<f t="array" ref="A1:Z1000">` and so on, each over a block, a 276 KB zip) took 110 s (5,000 took 5.8 s: quadratic), 1,000,000 ordinary formulas (a 7 MB zip) took 82 s and 2.1 GB of process memory, and 1,000 sheets each holding one formula that names the next took 33 s (400 took 4.6 s). The time is the recalculation that `setData` ran (reading each referenced cell, collecting dependencies, resolving sheet names), in engine code that the reader change did not touch; since S4 an imported file keeps its saved results instead of evaluating every formula on load (see "Formula interchange and cached values"), which saves the evaluation but not the parse or the dependency graph (100,000 ordinary formulas, `A1*2+1`, took 5.1 s through `importFromXlsx` with the saved results kept and 6.2 s with `recalculateOnLoad`, on a machine under load; 100,000 cached-only formulas, which have no graph node, took 3.8 s in both), so the advice above stands; array formulas are bounded by a per-sheet budget (1,000,000 cells): the 20,000 array formulas above now import in 1.2 s (and export in 0.3 s), 19,962 of them kept as saved values and reported as `xlsx.package.sizeLimit` (19,950 of 20,000 when they are dynamic arrays). A host should lower `maxTotalCells` (and `maxSheets`) and/or run the import in a worker; a faster load is a follow-up (`documentation/sheets/TODO.md`, candidate owner S20). A table of two million shared strings peaked at 2.8 GB of process memory in the reader alone (a 4 GB heap; five million entries took 1.17 GB, so the peak is not monotonic in the count): plan for 3 GB there.

In the React editor the limits are the `importLimits` prop of `WorkbookCanvas` (and the `limits` option of `importWorkbookFile`): `<WorkbookCanvas fileActions importLimits={{ maxTotalCells: 20_000_000 }} />`. The array formula budget is not one of the reader's limits: it has its own `maxArrayCells` prop (and `importWorkbookFile` option): `<WorkbookCanvas fileActions maxArrayCells={5_000_000} />`. What a limit cut is in the `loss` that `onFileOpened` receives; the editor shows nothing of it by itself (the pre-import dialog inspects the file's bytes and does not run the import, and there is no notice component for import warnings), so a host that raises or keeps the defaults should read `loss` there.

Where the user sees it: the confirmation dialog asks before the import and runs on the bytes (the detector never counts cells), so it cannot show these items; `WorkbookCanvas` hands the `loss` of `importFromXlsx`, with the items, to the host's `onFileOpened({ fileName, warnings, loss })`, and no editor UI shows a loss after the import. That is a decision for review: the items are in the result and the callback, and a host that wants to tell the user (a banner, a toast) uses `describeImportLoss(loss)`.

The hostile shapes of the reviews are imported in a child process with a limited heap and a generous time limit by `hostile-memory.test.ts` and `reader-hostile.test.ts` (an out-of-memory exit or the time limit is the failure; nothing is read off the test process's own heap, which varies by Node version). They are skipped below 6 GB of memory (the container's limit where there is one, and 2 GB free where the platform says), or when `XLSX_SKIP_HOSTILE` is set, and run at most one to three children at a time over all the jest workers of a machine.

## Confirmation dialog

The sheets and docs editors (when `fileActions` is on) check the file before replacing the open document. If the report is empty the file opens
straight away; otherwise an **Import anyway / Cancel** dialog lists what would be lost. Cancel (or Escape) leaves the document untouched and
`onFileOpened` is not called.

```tsx
<WorkbookCanvas fileActions importConfirmation="dialog" />        // default
<WorkbookCanvas fileActions importConfirmation="never" />         // import silently
<DocumentEditor fileActions
  importConfirmation={async (report, file) => myConfirm(file.name, describeImportLoss(report))} /> // your own UI
```

`ImportConfirmDialog` (props `{ fileName, report, onConfirm, onCancel }`) is exported by `@b32nio/spindle-shared/react` and re-exported from the
sheets, docs and slides React packages for hosts that build their own Open flow.

### Kept content (opaque elements, plan K11)

`importPptx` keeps what the editor can neither edit nor draw as **opaque elements** (`PptxOpaque`: `chart`, `smartArt`, `ole`, `media`, `ink`) and
stores the parts they refer to byte for byte in the opaque part store (`PresentationImportResult.opaqueParts`, content-addressed, 25 MiB per part and
200 MiB in all by default, `opaqueLimits` to change them). A chart keeps its chart part, embedded workbook, style, colour and theme-override parts; a
SmartArt diagram its data, layout, quick-style, colours and cached drawing parts (the drawing is not turned into shapes); an OLE object its
object part and preview picture; an audio or video clip its media part and poster frame; ink its ink part; an ActiveX control (`p:control`) its
control part and picture. The relationship part of every kept part is kept with it (role `rels`) so an export can rewrite the targets. Linked clips
and objects are never fetched: the address is kept inert. A slide's transition and timing tree are kept as XML fragments in `PptxSlide.opaque` and
`Slide.opaque` in the editor; the timing names shapes by `pptxId` and is pruned when the shape is deleted. `exportPptx` (plan K14) writes them
back: each part byte for byte from the store (under its own name where the package has no use for it, else renamed, with the relationship
parts rewritten to match), the frame that names them, and the transition and timing XML of each slide. Left out and reported: linked clips
and objects (no link to them is written on the slide), ActiveX controls, extended charts (`chartEx`, a follow-up), a timing that names a shape the slide does not hold under the same id, and the sound of a
transition. External relationships inside a kept part's own relationship part (a chart's linked workbook, a hyperlink) stay as they were:
they are inert, nothing is fetched. The loss report says `kept` because the parts are stored (an export writes back what it can, and says what it
leaves out; the exceptions above are reported as changes on export), and the placeholder in the editor says "(kept, not editable)".
